# Review 02 (adversarial): server and game layer — verdict on the Opus report

Scope: everything `02-server-game-opus.md` claims about `server/index.ts`, `server/gamify.ts`, `server/progress.ts`, `server/content.ts`, `content/types.ts`, `scripts/e2e.ts`, plus what it missed. Every claim was checked against the code at the cited lines; the important ones were reproduced against a live server on `:4598` with a fresh save (backed up first, restored afterwards). Economy numbers were re-derived with the real `computeXp`, `levelFromXp`, `rollDailyQuests`, `readiness` and the real curriculum, not a hand model.

Two environment notes that matter for reading the evidence below:

- The `:4598` instance my probes hit was the one the previous partial run had left listening (PID 17500, started 13:51). My own `PORT=4598` start died with `EADDRINUSE`. It ran the same unmodified `server/*.ts` against the same `data/progress.json`, so the results stand; the crash probe at the end killed it, and nothing is listening on 4598 now.
- The machine was at **100% CPU with ~40 node processes** (other agents building and testing) during my session. That exposed a structural bug (below) but it also means wall-clock timings are pessimistic.
- The web tree is being rewritten by someone else right now (uncommitted: 9 files, `web/src/pages/lesson/` untracked). The new UI reads `lesson.xpAtStake`, `lesson.next.id`, `lesson.next.unlocked` and a `'mutation'` kind that `publicLesson` (`content.ts:216-246`) does not send (`next` is a string id). Out of my scope, but whoever builds from this review must sync `publicLesson` or the UI will break.

## Verdict on the report

The Opus report is **reliable on the code-level facts and sloppy on a handful of details**. All 16 findings point at real code, and the four it calls high (double reward, crash on malformed body, unlocked `/solution`/`/hint`/`/run`, `0.0.0.0` bind) reproduce exactly. Its economy arithmetic is correct to the XP (level thresholds, 5,085 achievement XP, 3,965 guaranteed, 224.9 quest XP/day, 10,151 lesson XP for Run-then-Submit, L20 floor). Where it goes wrong it is by overreach: the "+46%" number is measured against its own simulated "typical" learner rather than the floor (+50%), "13 lessons have 6–8 hints" is 7, locked-lesson records do **not** drive `nextUp`, the `Lesson.tsx` "stale closure" is really a re-render gap, `mid-level` is not "never earnable" after an orphan (it can also fire early), and `/run` on a quiz burned a 10 s timeout for me rather than returning "no tests". None of these change the shape of the fixes.

The bigger problem is what it did not look at. It never ran two gradings in the same second on purpose beyond the double-pay repro, so it missed that **the grading budget starts before the worker has finished booting** and that **sandbox/infrastructure failures are scored as the learner's failed attempts**: under load, correct code timed out on 2 of 4 *sequential* submits, each logged as `fail`, counted as an attempt, and reset the combo. It also missed that the sandbox has `child_process` and the network (not "filesystem access" only), that two server processes sweep each other's run directories, that `/reset` is one `curl` away for anyone on the LAN, and that the Stats page's "of 6,785 available" is false the moment a badge pays out. Its recommendation section is where it is weakest: the 25-file refactor tree, the mastery-derived rank and the spaced-repetition system are all disproportionate to a 445-line single-learner server, and the "hidden tests" preference does not survive an authoring-cost estimate.

## What Opus missed

1. **The grading budget includes worker boot, so infrastructure failures are scored as the learner's failures.** `runner/index.ts:73-74` takes `started` and arms the 10 s timer (`:99`) *before* `new Worker` (`:80`); the worker then does `import ts from 'typescript'` (`worker.mjs:13`), which cost 0.9–3.4 s in an isolated worker on this box and 6–8 s under load. Measured: four *sequential* single submits of correct `js-closure-state` code → `seq0 ok wall 7.3 s`, `seq1 ok 6.1 s`, `seq2 TIMEOUT`, `seq3 TIMEOUT`; a 400 ms-staggered pair → both `TIMEOUT`, history `fail fail`, `stats.submits 2, passes 0`. Each of those went through `index.ts:357-366`: `attempts++`, `combo = 0`, a `fail` log entry, first-try gone. Nothing distinguishes "your loop never ended" from "the sandbox never started". The learner sees "Timed out after 10s. An infinite loop…" for correct code. This is the highest-value miss in the report.
2. **Two server processes sweep each other's run directories.** `index.ts:437` `void sweepRunsDir()` → `runner/index.ts:19` `rm(RUNS_DIR, recursive)` on every start. `tsx watch` restarts (`npm run dev:api`) and Opus's own advice to run e2e on another `PORT` both delete in-flight `.runs/<uuid>` dirs of the other process, which then fails at `import(url)` with a "threw while loading" result, and (per #1) that counts against the learner.
3. **The sandbox has `child_process` and the network, not just the filesystem.** Opus stopped at `readFileSync`. `execSync('whoami')` and `fetch` to the API both work from learner code. With the `0.0.0.0` bind (Opus #4) this means remote code execution as the user; even locally it means a pasted "solution" from a forum can `POST /api/reset`.
4. **`/reset` is unauthenticated on a network-exposed server.** `index.ts:410-416` only checks `confirm === 'RESET'`. Anyone on the LAN can wipe the save with one `curl`; DNS rebinding makes it same-origin for a browser too. Opus listed `/reset` only as "can't be undone".
5. **The Stats page lies about available XP.** `profile.xpAvailable = totalXp` (`index.ts:49`, 6,785) is rendered as "of 6,785 available" (`Stats.tsx:42`, `TrackMap.tsx:14`), but `p.xp` includes 5,085 of achievement XP and unbounded quest XP. A learner will read "7,300 of 6,785 available". Either report `xp` split into lesson/meta, or make the denominator honest.
6. **The README's streak promise is broken at the start, not just after a gap.** `fresh()` (`progress.ts:62`) hands out `freezes: 1` on day zero; README says freezes are "earned (one per 5-day streak)". Also `bumpStreak` runs only inside `applyPass`, so after 100% completion (or on a day spent re-practising passed lessons) nothing can extend the streak; Opus noted "nothing earns XP after 100%" but not that the streak dies too.
7. **`day.xp` counts lesson XP only.** `applyPass` adds `breakdown.total` to `day.xp` (`index.ts:195`) but quest and achievement XP go straight to `p.xp` (`:209, :221`). "Earn 300 XP" is really "earn 300 *lesson* XP"; the dashboard's day counters and the profile disagree by design and nobody documents it.
8. **`mid-level` can fire early, not only never** (see table #10): 71 real + 1 orphan = 72.
9. **No boss gate anywhere in the unlock rules.** With the 70% rule (or Opus's "all but one") a boss is just the last lesson, so every boss is exactly the one lesson you are allowed to skip. "Boss Slayer" needs 3 of 8 and `track-*` badges need 100%, but nothing stops a learner reaching chapter 4 of a track with zero bosses passed. Decide deliberately (I recommend: skippable for unlock, required for the track badge and Mid-Level, which is already the case) and state it in the README.
10. **`/run` on a quiz burns a full worker boot** (10 s timeout observed) instead of a 400; `sandboxMs` grows by 10 s per click, and under load it makes the UI look hung.

Smaller: `record()` on `/hint` returns early at `index.ts:287` without saving, so the record it may have just created is only persisted by the next unrelated save; `store.today(p)` in `syncQuests` creates an empty `days[today]` entry on every dashboard load; `history` entries for `fail` carry no XP and the `/state` slice is 40 while the cap is 300, fine but undocumented.

## Challenges to the recommendations

**"Hidden tests on Submit" (Opus A, preferred).** Pedagogically it is less bad than it sounds: test *code* is never sent to the client anyway (`publicLesson` strips `tests`), so a hidden test failing on Submit shows the same name and assertion message as a visible one does today. The learner is not blind; they just cannot iterate on it for free. The real objections are cost and trust: 62 graded lessons need a curated visible/hidden split, the harness needs `it.hidden`, `npm run verify` needs to check both halves, and every lesson where the hidden half is wrong is a lesson that silently strands people. And "Run says green, Submit says red" is exactly the surprise the README promises not to spring. **Rejected for now.** "Run costs a little" is worse: it taxes the behaviour the README explicitly invites ("Experiment freely") and pushes people to Submit blind, which is the guessing the README says it discourages. **Take Opus's "cheaper" option**: delete the first-try bonus and the combo, add a clean bonus. It is honest under any Run strategy, and it is a 30-line change.

**Rank by skill (Opus D/F).** There is no skill model in this codebase, and Opus's "mastery" is not one; it is `1 − 0.08·hints − 0.04·(attempts−2)`, i.e. the same hint/attempt counters that already reduced the XP, now penalising a second time, and just as gameable by Run-until-green as the first-try bonus it replaces. Ranking on it would tell a learner who used hints on a boss that they are less "mid" than one who pasted the solution after a Run-until-green loop. **Rank should come from completion milestones plus bosses**, which are structural facts the code already has (`readiness.per`, `passed.filter(r => r.boss)`), need no new state, and cannot be gamed except by passing lessons. Keep levels as XP feedback. Drop "Senior-Track" (Opus is right that a junior→mid course cannot certify it).

**JSON vs PGlite.** PGlite is in `package.json` for the SQL track, but using it for the save would add a 1–2 s WASM boot to server start, an in-process instance eating ~50–100 MB alongside the ones the sandbox spins up per SQL lesson, and a binary data directory that is neither diffable nor safely copyable while running, which is the README's whole argument for JSON. Every real persistence risk Opus found (corrupt-file wipe, no fsync, fixed `.tmp`, no backup, no lock) is solved by about 60 lines around the existing file. `node:sqlite` exists on Node 24 but is out of the stated stack. **Keep JSON**, with the additions below.

**Split `index.ts`.** It is 445 lines with four concerns and one import graph; Opus's answer is a 25-file tree with `domain/`, `projections/`, `services/`, `store/`, `http/routes/` and a `shared/`. For a single-learner app that is architecture for its own sake, and it moves the pure `gamify.ts` (which is already the well-factored part) into six files. **Do a 4-file split** and, more importantly, export `createApp()` so routes can be tested without a port, and add the unit tests for `gamify.ts` first; they catch more than any directory layout. `shared/api.ts` for wire types is worth doing (the drift is real), especially since the UI is being rewritten right now.

**Spaced repetition, Leitner boxes, per-tag weak spots (Opus E/G).** Good ideas, wrong review. They are new features, not fixes, and E in particular needs UI, a review queue, quest changes and a migration. Park them behind the must/should list.

## FINAL RECOMMENDED CHANGES

Ordered by execution; each has the concrete rule. Stack stays Express 4 + TS. Items in one numbered group are one PR.

**MUST — stop the bleeding (one PR, plus e2e cases for each)**

1. **Bind loopback and check Host.** `app.listen(PORT, '127.0.0.1', cb)`. First middleware: `if (!/^(localhost|127\.0\.0\.1|\[::1\])(:\d+)?$/i.test(req.headers.host ?? '')) return res.status(421).json({ error: 'Bad host' })`. Log the URL as `http://127.0.0.1:PORT`.
2. **Async safety and input validation.** `const h = (fn) => (req, res, next) => Promise.resolve(fn(req, res, next)).catch(next)` on every route. Final error middleware: JSON only, `status = err.status ?? err.statusCode ?? 500`, body `{ error }` with the message for 4xx and `'Internal error'` for 5xx, `console.error` for 5xx. Body parser: `express.json({ limit: '128kb' })` with its `entity.parse.failed` mapped to `400 { error: 'Malformed JSON' }`. Validators: `code` must be a string, else 400; length > 60,000 → 413; store drafts with the same 60k cap on `/draft`, `/run` and `/submit`. `answers` must be an array whose items are arrays of non-negative integers, else 400; ignore anything past `quiz.length`. `confirm` must be the string `'RESET'`.
3. **Lock everything that leaks or mutates.** `requireUnlocked(loc, p)` → `403 { error: 'Lesson is locked' }` on `/hint`, `/solution`, `/run`, `/draft` and `/submit`. Leave `GET /lesson/:id` open (brief and starter are fine to read; UI shows the lock). `/run` and `/submit` on a `quiz` lesson without `answers` → `400 { error: 'Quizzes are answered, not run' }` **before** any sandbox call.
4. **One grading at a time, and no double pay.** Module-level `const inFlight = new Set<string>()`: a second `/run` or `/submit` for the same lesson id while one is in flight → `409 { error: 'Already grading this lesson' }`. Global semaphore of **1** around `runExercise` (a single learner never needs two; parallel workers only add boot contention, see 6). In `/submit`, take `rec`/`alreadyPassed` **after** the `await`; everything after that await is synchronous and therefore atomic.
5. **Do not score the sandbox's failures as the learner's.** Define `scored = result.tests.length > 0 || result.phase === 'compile' || result.phase === 'load' || (result.timedOut && result.ready)`. Only a scored failure increments `attempts`, resets `combo`, logs `fail`. Unscored results return `{ result, scored: false }` with `result.error` and no state change. Requires 6.
6. **Runner: start the clock when the worker is ready.** Worker posts `{ ready: true }` after its imports; parent arms the per-kind budget on `ready` and sets `result.ready = true`; a separate 30 s boot timer yields `phase: 'boot', error: 'The sandbox took too long to start'`. Per-process run root `.runs/<pid>/`; `sweepRunsDir` removes only directories older than 1 h or belonging to dead PIDs.
7. **Combo and post-pass actions.** `p.combo = 0` only when `!alreadyPassed`. On pass, freeze `rec.pass = { attempts, hintsUsed, solutionRevealed, at }` and make `no-net`, `flawless`, `chapterStats.allFirstTry` read from `rec.pass`; post-pass hint/solution reveals update `rec.hintsUsed`/`solutionRevealed` for display only.
8. **Fix the quotes.** `xpAtStake` uses `attempts: rec.attempts + 1` in `/submit` failure responses and honours `rec.solutionRevealed` in `/hint`; `/solution` returns `xpIfPassed: alreadyPassed ? 0 : round(base*0.2)`; `computeXp` revealed branch returns `hintPenalty: 0`.
