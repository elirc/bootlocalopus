# Adversarial review of `03-frontend-opus.md`

Scope: every claim in the Opus report checked against `web/src/**`, `vite.config.ts`, `scripts/ui-smoke.mjs`, `server/index.ts`, `server/content.ts`, `server/progress.ts`, `server/gamify.ts`, `tsconfig.json`, and the installed `node_modules` for `@codemirror/commands@6.11.0`, `@codemirror/view@6.43.11`, `@uiw/react-codemirror@4.25.11`, `@uiw/codemirror-extensions-basic-setup`. I ran `npx vite build` into a scratch directory. No code was changed.

## Verdict on the Opus report

The report is reliable on facts and unreliable on proportion. Every file:line citation I checked resolves to what it says it does, and the four load-bearing technical claims all hold: `defaultKeymap` binds `Mod-Enter` to `insertBlankLine` and CodeMirror does not stop propagation for it; `@uiw/react-codemirror` really does skip `onChange` for prop-driven changes; the server really does zero the combo on a failed submit to an already-passed lesson; and the `.md table >= 0` smoke check really cannot fail. The bundle numbers are exact (740.61 kB / 246.02 kB gzip). The errors are in the details and the framing: the "stale snapshot" half of finding #1 is a whitespace-only difference in practice; "2.5k lines of TSX" is 1,701; a quote attributed to the README is a server comment; the file has five components, not "three" (summary) or "four" (structure section); the `autocompletion: false` suggestion under the bundle heading does not remove a byte; and finding #10 says focus stays on the Submit button while finding #11 correctly says the disabled button drops focus to `<body>`. The bigger problem is that the fixes are sized for a different app: a ~30-file tree with a `hooks/` layer and a `features/lesson/` directory of eleven files is proposed for 1.7k lines, when the real bugs (a stale closure in a window listener, an uncancelled timer, a `lesson` object that is never patched) are each a few lines. Opus also missed a server-side interaction with worse consequences than most of what it found: the draft autosave marks every lesson you type in as "attempted", which hijacks the Dashboard's Continue button, and revealing the solution on a passed lesson silently disqualifies two achievements.

## What Opus missed

1. **Typing in the editor marks the lesson "attempted" and hijacks the Dashboard's Continue button.** `store.record()` (`server/progress.ts:109-115`) get-or-creates a `LessonRecord` with `status: 'attempted'`, and it is called from `/draft` (`index.ts:276`), `/run` (`:319`), `/hint` (`:286`) and `/solution` (`:306`). So the 800 ms autosave after one keystroke flips a lesson to `attempted`. `nextUp` (`content.ts:84`) prefers any unlocked `attempted` lesson in curriculum order, so glancing at a JS lesson and typing a character makes "Continue" point there forever, ahead of the SQL lesson you were actually working through; `trackTree` (`index.ts:135`) shows the accent marker (`styles.css:270`) on it too. The README says Run has "no attempt counted, no combo lost" (line 101); it does not say it re-routes your dashboard. Opus read `nextUp` for #8 and this route for #7 and did not connect them.

2. **Revealing the solution or a hint on an already-passed lesson silently disqualifies achievements.** `/solution` sets `rec.solutionRevealed = true` regardless of status (`index.ts:306-307`); `/hint` bumps `hintsUsed` (`:288`). `chapterStats.allFirstTry` (`content.ts:68-70`) is `firstTry && !solutionRevealed`, which gates **Flawless** (`gamify.ts:230-231`), and **No Safety Net** counts `hintsUsed === 0 && !r.solutionRevealed` (`gamify.ts:234-235`). Opus's own #3 says comparing with the reference "is where the learning happens", and the UI keeps both buttons live after a pass (`Lesson.tsx:111-115`, `:229-233`) with cost labels ("−12% XP", "worth 20% of the XP") that are meaningless post-pass. The learner pays with a badge they were never told about. Fix is server-side (skip the flags when `rec.status === 'passed'`) plus post-pass labels in the UI.

3. **`alreadyPassed` is declared and never read.** `api.ts:174` types it; `grep alreadyPassed web/src` finds only that line. On a passed lesson, `handle` (`Lesson.tsx:178-179`) treats a green re-submit as a pass with no rewards and says nothing; a red re-submit shows failures and says nothing about the combo it just zeroed (#2). One banner ("Already cleared — re-submits earn no XP") is the smallest fix; F8 is the full one.

4. **No error boundary.** `main.tsx:6-10` renders `<App/>` bare. Any render-time throw (a lesson with `tags: undefined` would be caught by `content.ts:101`, but `marked.parse` on a bad brief, a `quiz` entry with no `options`, or a future field rename) blanks the page with nothing in the UI. This matters more here than in most apps because the README invites people to add lessons (line 157) and the content lint is a separate script.

5. **Contrast fails on small text.** `--text-faint: #6b7683` on `--bg: #0e1116` (`styles.css:12`, `:4`) is about **4.07:1**, under WCAG AA's 4.5:1, and it is used at 9.5 px (`.ring-caption`, `:175`), 10.5 px (`.nav-section`, `:120`), 11 px (`.timeline-when`, `:563`), 11.5 px (`.stat-label`, `:187`; `.quest-meta`, `:215`), 12 px (`.lesson-crumbs`, `:298`; `.lesson-why`, `:273`). The shortcut hint inside the primary button is `opacity: 0.6` on the accent background (`Lesson.tsx:219`). Bumping the token to `#7d8794` (about 5.2:1) fixes all of it in one line; Opus's a11y sweep covers structure but never measures colour.

6. **The window keydown listener is re-registered on every keystroke, and that is the real cause of #1b.** `handle` depends on `code` (`Lesson.tsx:193`), the effect depends on `handle` (`:206`), so every `onChange` tears down and re-adds a window listener. A `useRef` holding the latest `handle` (or reading the editor's document directly) fixes the stale closure without a `useHotkey` hook or a `useDraft` hook. Opus's fix (keymap inside CodeMirror through a ref) is right; its diagnosis blames the file layout rather than the dependency array.

7. **Dead-end error states in routing.** An unknown lesson id renders the raw server string (`No such lesson`) in a `.loading` div with no link anywhere (`Lesson.tsx:20`). An unknown track id silently shows the tracks index (`TrackMap.tsx:6-7`) with the sidebar highlighting nothing. Opus lists the 404 only as an untested smoke case, not as a UI gap.

8. **The sidebar loses track context on lesson pages.** Track items are active only when `route.name === 'tracks' && route.trackId === track.id` (`App.tsx:133`), so on the screen where learners spend most of their time no track is highlighted and the only orientation is the crumb line. Also `track.title.split(' ')[0]` (`App.tsx:140`) yields "Engineering" for Engineering Craft; that is not a truncation strategy, it is luck for five of six tracks.

9. **The "Locked" screen is client-side theatre.** `GET /lesson/:id` (`index.ts:265-270`) returns `publicLesson` for locked lessons too, including the brief, starter and any revealed hints; only `POST /submit` checks `lessonUnlocked` (`:335`). `/hint` and `/solution` do not. Low severity on a local single-player app, but if the lock is meant to mean anything the server should return `{ unlocked: false, title, chapter, track }` and nothing else.

10. **Network-failure results show "0ms" and are indistinguishable from sandbox failures in the data model.** The catch path (`Lesson.tsx:182-188`) fabricates a `RunResult` with `ms: 0`; `ResultPanel` prints it (`bits.tsx:145`). Opus fixed the copy (#13) but the shape is the problem: a client-side error should be its own state, not a fake grader result that later gets cached (F7) as if the code had run.

## Challenges to the refactor plan

**The `features/lesson/*` tree and four hooks are over-engineering for this codebase.** The proposal lists roughly 30 files (`app/` 3, `api/` 2, `hooks/` 4, `components/` 9, `features/lesson/` 11, `pages/` 4, `lib/` 2, `styles/` 6+) for 1,701 lines of TSX today. `Lesson.tsx` at 524 lines is the only file with a size problem, and it splits naturally into four files (`Lesson.tsx` keeping `LessonView` + `Brief`, `CodePane.tsx`, `QuizPane.tsx`, `RewardCard.tsx`) without a `features/` directory or a `hooks/` directory. Of the four hooks: `useDraft` is the one with real logic (timer, flush, immediate save, status) and it is about 25 lines that can live at the top of `CodePane.tsx`; `useHotkey` becomes unnecessary once the shortcut is a CodeMirror keymap (a window fallback for when focus is outside the editor is 8 lines and arguably should not exist, since Ctrl+Enter in the brief pane has no editor meaning); `useAppState` is the existing `refresh` plus a sequence counter and a `fatal` derivation, about 15 lines inline in `App.tsx`; `useLesson` with `applySubmit`/`applyHint` is two `setLesson(l => ({...l, ...}))` calls. Opus says "the tangle is the direct cause of #1, #4, #5 and #7". It is not: #1 is a dependency array, #4 is an uncancelled timer, #5 is a missing `setLesson`, #7 is a missing ignore flag. All four are fixable in place in under 40 lines total. Do the split for readability; do not do it as the vehicle for the bug fixes, and do not add a `hooks/` layer until a hook is used from two places.

**`shared/api-types.ts` + `satisfies` is sound but heavier than needed, and the reason given for rejecting the alternative is wrong.** With this `tsconfig.json` (`moduleResolution: "bundler"`, `allowImportingTsExtensions: true`, `include: ["server","content","web/src","scripts","vite.config.ts"]`) a `shared/` directory is not in `include` but gets pulled in transitively by whichever side imports it, and `export type * from` is erased by esbuild so nothing reaches the bundle. That works. But `server/` and `web/src/` are *already one tsc program*, so "it pulls server modules into the web type graph" is not a cost anyone pays today. The cheapest correct change is zero new files: keep the interfaces where they are in `web/src/api.ts`, have the server `import type { AppState, Profile, LessonDetail, SubmitResponse, Rewards } from '../web/src/api.ts'`, annotate `profile(p): Profile`, `publicLesson(...): LessonDetail`, `applyPass(...): Rewards`, and `res.json({...} satisfies AppState)`. Drift then fails `npm run typecheck` on the server side exactly as Opus wants. Move the file to `shared/` later if the odd import direction bothers anyone; it is a `git mv`. Two cautions either way: use `import type` (not `import { type X }` mixed forms) so erasure is unambiguous with `verbatimModuleSyntax: false`, and the `Rewards.xp` literal in `api.ts:153-161` should become `XpBreakdown` from `gamify.ts` (it already matches field-for-field; I checked `gamify.ts:50-58`). I found no existing drift between `api.ts` and the server projections; the extra `metric`/`kind` fields on `Quest` (`gamify.ts:137-146`) are harmless.

**Lazy-loading CodeMirror is not worth it on localhost, and Opus half-admits this.** The one route without an editor is the Dashboard, whose primary action is a button into a lesson, so the chunk is needed within seconds of first paint in nearly every session. The asset is hash-named and cached after the first load; the one-time parse of 740 KB on a modern V8 is tens of milliseconds and V8 lazily compiles function bodies anyway. Adding `React.lazy` introduces a loading flash on the primary route and a `Suspense` boundary to reason about. The only concrete thing the change buys is silencing the build warning, which `build: { chunkSizeWarningLimit: 900 }` in `vite.config.ts` does in one line. The README (line 212) already made this call and made it correctly. If it is done anyway, `Markdown` must leave `bits.tsx` first or `marked` stays in the main chunk because `Dashboard` imports `bits`. Tag: could, last.

**The CSS plan is fine in substance, oversized in form.** 592 lines in one file is not a problem; six partials is bookkeeping. Promote the 37 hex literals to tokens (this is the whole prerequisite for a light theme and it is mechanical), add `:focus-visible` and `prefers-reduced-motion`, fix the contrast token, and replace the *repeated* inline styles (`color: var(--text-dim)`, `fontSize: 13`, `marginTop: N`) with three or four classes. The `--track` custom-property trick for badge tints is good. Leave the one-off inline styles alone.

**`Modal` on `<dialog>` is the one new component that pays for itself.** Agreed: reward card, reset confirm, solution confirm. Keep it under 30 lines.

**The smoke-test plan is right.** `DATA_DIR` from env is a one-line change in `server/progress.ts:12`; the golden-path test (Solution → Submit → reward → sidebar count) catches #3, #5 and #10 at once. The shortcut test needs the editor focused inside jsdom, which works because CodeMirror's keymap runs on `keydown` dispatched to `.cm-content`.
